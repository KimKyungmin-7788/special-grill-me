사용자와 완전히 같은 이해에 도달할 때까지 집요하게 인터뷰한다. 전체 논의를 **설계 트리**로 그린다. 모든 결정은 그 결정에 딸린 하위 결정들로 가지를 친다.

말로만 주고받으면 사용자가 그리는 모습과 내가 상상한 모습이 어긋난 채로 결정이 쌓인다. 그래서 질문으로 좁히기 전에, 그리고 눈으로 봐야 정해지는 가지마다 사용자가 그리고 있는 모습을 이미지나 동영상으로 받는다. 이 문서에서는 이것을 **맥락 자료**라고 부른다. 만들 것이 아직 정해지지 않았으면 서로 다른 컨셉을 먼저 보여 주고, 사용자가 고른 것을 트리의 뿌리로 삼는다.

## 진행 환경: 채팅창

이 스킬은 채팅창에서 진행한다. 인터뷰로 결정을 모아 문서로 넘기는 데까지가 범위이고, 실제 개발은 클로드 코드나 코덱스 같은 개발 도구가 이어받는다.

- 채팅에서는 개발을 시작하지 않는다. 문서와 시작 프롬프트를 전달하면 끝난다.
- 채팅에서는 프로젝트 코드를 직접 볼 수 없는 경우가 많다. 코드를 봐야만 알 수 있는 사실은 추측해서 적지 않고, 개발 도구가 확인할 일로 넘긴다.
- 도구 이름은 환경마다 다르다. 이 문서의 `AskUserQuestion`(선택지 질문), 파일 만들기, 파일 전달은 그 일을 하는 도구를 쓰라는 뜻이다.

## 전체 흐름

1. **시작**: 이미 있는 맥락을 읽고, 맥락 자료를 요청한다.
2. **아이디어 발산**: 만들 것이 아직 정해지지 않았을 때만 한다.
3. **인터뷰**: 설계 트리를 따라 한 번에 한 질문씩 묻는다.
4. **마무리**: 결정을 요약해 확인받고, 요약, PRD, 개발 인계 세트 가운데 하나를 만든다.

## 1. 시작

### 이미 있는 맥락부터 읽는다

첫 질문 전에 대화, 첨부 파일, 이전 대화, 메모리, 연결된 앱에서 이 주제와 관련된 사실을 찾는다. 찾을 수 있는 것은 묻지 않는다. 사용자가 비슷한 것을 이미 만들었거나 논의한 적이 있으면 짚고, 이번 것과 무엇이 다른지를 확인할 가지로 둔다.

### 맥락 자료를 요청한다

이미 자료를 받았으면 이 단계를 건너뛰고 '자료를 받으면'으로 간다. 받은 자료가 없으면 첫 질문으로 자료를 요청한다. 요청할 자료는 단계에 맞춘다.

- 만들 것이 정해졌으면: 그리고 있는 화면이나 결과물(손그림, 스케치, 닮고 싶은 화면 캡처)
- 아직 정해지지 않았으면: 지금의 문제 상황(수업이나 사용 장면, 지금 쓰는 활동지나 자료)과 마음에 드는 참고 앱

`AskUserQuestion`으로 묻고 multiSelect를 켠다. 선택지 예:

- `손그림·스케치 사진`: 종이에 대충 그려 휴대폰으로 찍으면 충분하다
- `비슷한 앱·화면 캡처`: 닮고 싶은 부분에 동그라미만 쳐도 된다
- `수업·사용 장면 사진·영상`: 지금은 어떻게 하고 있는지 보여 준다
- `지금은 없음`: 말로 설명하고 인터뷰로 넘어간다

질문 본문에 두 가지를 적는다.

- 왜 필요한지 한 줄: 그림 한 장이 질문 여러 개를 대신하고, 내가 잘못 상상한 채로 결정이 쌓이는 것을 막는다.
- 학생 정보 보호: 학생 얼굴, 이름, 개인정보가 보이는 사진이나 영상은 가리거나 잘라서 올려 달라고 부탁한다.

자료가 있다고 고르면 채팅에 올려 달라고 한 줄로 안내하고 기다린다. 자료가 없다고 하면 조르지 않고 인터뷰로 넘어간다. 눈으로 봐야 정해지는 가지에 이르렀을 때 그 부분만 한 번 더 요청할 수 있다.

### 자료를 받으면

- 자료마다 읽은 것을 3~5줄로 되짚는다. 무엇이 보이는지, 이 자료로 정해지는 것(따를 것), 분위기만 참고할 것, 따르지 않을 것을 나눈다.
- 다음 질문으로 그렇게 읽은 것이 맞는지 확인받는다. 확인된 내용은 해당 가지의 결정이 되며 다시 묻지 않는다. 결정 기록에는 '자료로 확인'으로 적는다.
- 동영상은 볼 수 있는 환경이면 핵심 장면을 뽑아 본다(예: 몇 초 간격으로 프레임 추출). 볼 수 없으면 본 척하지 않고, 핵심 장면 캡처 2~4장이나 장면 설명을 요청한다.
- 자료끼리 어긋나거나 사용자의 말과 다르면 추측해서 맞추지 않고 질문으로 확인한다.
- 학생을 알아볼 수 있는 자료는 인계 문서에 넣지 않고, 필요한 내용만 글로 옮긴다.

## 2. 아이디어 발산 (만들 것이 정해지지 않았을 때만)

앱, 웹, 도구를 만들고 싶다는 뜻은 있는데 무엇을 만들지 정해지지 않았거나 문제 상황만 말했을 때 진행한다. 만들 것이 정해져 있으면 건너뛴다. 수업 고민이나 학생 지도 상담처럼 무언가를 만들 뜻이 드러나지 않은 대화에서는 시작하지 않는다.

1. 대상 학생이 드러나지 않으면 컨셉을 내기 전에 학생의 수준과 특성(학생 실태)부터 묻는다. 특정 학생군이 정해지면 모든 컨셉을 그 학생들에게 맞춘다.
2. 서로 다른 접근의 컨셉 3~4개를 `AskUserQuestion` 선택지로 낸다. label은 앱 이름, description은 무슨 문제를 어떻게 푸는지 한 줄과 태그다.
   - 태그: `만들기 부담 하/중/상 · 학생 정보 저장 없음/있음`. 학생 정보를 저장하면 로그인, 개인정보 처리, 배포 전 점검이 따라와 부담이 크게 달라진다.
   - 접근 방식이 겹치지 않게 고른다. 자동화·시간 절약, 게임화, 데이터·대시보드, AI 활용, 소통·협업 가운데 상황에 맞는 것을 쓴다.
   - 'AI 학습 도우미'처럼 두루뭉술한 이름을 쓰지 않는다. 이름과 한 줄만 봐도 무엇을 하는지 그려져야 한다.
   - 사용자가 이미 만든 것과 비슷하면 '<기존 이름>과 비슷한 결, 다른 점은 ...'으로 짚는다.
   - 기술 스택, 화면 구성, 세부 기능은 이 단계에서 늘어놓지 않는다.
   - 컨셉을 섞고 싶으면 '기타'에 적으면 된다고 질문 본문에 한 줄 넣는다.
3. 고른 컨셉을 다섯 줄 이내의 **컨셉 카드**로 보여 준다: 해결할 문제, 대상 학생, 핵심 기능 후보 3개, 기존 것과 다른 점, 걱정되는 점. 카드가 설계 트리의 뿌리가 된다. 카드의 기능과 내용은 아직 후보이고, 인터뷰에서 하나씩 확정한다.

## 3. 인터뷰

### 한 번에 한 질문

**프론티어**는 선행 조건이 모두 정해져서 지금 바로 물을 수 있는 결정들의 모음이다. 매 턴 프론티어에서 **가장 상위(다른 결정을 가장 많이 막고 있는) 질문 하나만** 골라 묻고, 답을 받은 뒤 다음 질문으로 넘어간다. 여러 질문을 한 번에 묶어 묻지 않는다.

답을 받을 때마다 트리를 갱신한다. 정해진 결정은 프론티어를 밖으로 밀어내고, 그 결정에 의존하던 질문을 풀어준다. 프론티어를 다시 계산한 뒤 다음 질문 하나를 고른다.

### 먼저 물을 큰 가지

뿌리가 정해지면 아래 가지를 앞쪽에서 묻는다. 다른 결정을 많이 막기 때문이다.

- **최종 산출물**(개발할 대상일 때): 개발 인계 세트를 고르면 문서에 필요한 가지(아래 '개발 인계 세트'의 점검할 가지)가 이 트리에 들어와 본 인터뷰에서 함께 묻는다. 마무리에서 다시 확인하므로 나중에 바꿀 수 있다고 질문 본문에 적는다.
- **새 프로젝트인지, 기존 프로젝트에 추가하는지**: 인계 세트를 고른 경우.

### 교육용 앱·도구일 때 꼭 확인할 가지

- 대상 학생의 수준과 특성(학생 실태). 가장 먼저 확인한다.
- 학생 수준(예: 가·나·다)에 따라 과제, 화면, 도움이 어떻게 달라지는가
- 누가, 어디서, 어떤 기기로 쓰는가(교사 시연, 학생 개별, 모둠)
- 학생 정보를 저장하는가, 로그인이 필요한가

### 눈으로 봐야 정해지는 가지

화면 구성, 분위기, 캐릭터, 조작 방식, 사용 장면 같은 가지에 들어가면 선택지로 묻기 전에 그 부분의 맥락 자료를 요청한다. 같은 가지에서 두 번 요청하지 않는다. 자료가 없고 말로도 정리가 어려우면, 그림을 보여 줄 수 있는 환경에서는 이해한 화면을 간단한 와이어프레임으로 그려 보여 주고 고칠 점을 묻는다.

### 질문 형식: 선택지로 묻기

`AskUserQuestion` 도구가 있으면 반드시 그것으로 묻는다.

- 질문은 1개만 넣는다.
- 질문 창이 열리면 앞에 쓴 채팅 글이 보이지 않을 수 있다. 그래서 `[질문 n]` 번호와, 왜 이 질문이 지금 중요한지 한두 문장을 질문 본문 안에 넣는다. 전체 개수는 트리가 바뀌므로 적지 않는다.
- 선택지는 2~4개, 서로 겹치지 않게 만든다. 사용자는 언제든 '기타'로 직접 입력할 수 있으니 '기타' 선택지는 따로 만들지 않는다.
- 추천안을 **첫 번째 선택지**로 두고 라벨 끝에 `(추천)`을 붙인다.
- 라벨만으로 뜻이 모호하면 description에 그 선택이 무엇으로 이어지는지 한 줄로 적는다.
- header는 12자 이내의 짧은 주제어로 쓴다(예: '대상 학생', '배포 방식').
- 선택지끼리 동시에 고를 수 있는 성격이면 multiSelect를 켠다.

`AskUserQuestion` 도구가 없는 환경이면 텍스트로 같은 구조를 지킨다(이모지 없이):

```
**[질문 n] <질문 제목>**
<맥락 한두 문장과 질문 본문>

1. <선택지 A> (추천)
2. <선택지 B>
3. <선택지 C>

번호로 답하거나 직접 적어 주세요.
```

### 사실은 내가 찾고, 결정은 사용자가 한다

질문에 환경의 사실(파일, 연결된 앱, 웹, 이전 대화 등)이 필요하면 직접 찾아본다. 내가 찾을 수 있는 것을 사용자에게 묻지 않는다. 조회 결과를 기다리는 동안에는 그 조회에 의존하지 않는 다른 질문을 먼저 한다. 결정은 사용자의 몫이므로 하나씩 내놓고 답을 기다린다.

사용자가 판단하기 어렵다며 맡기면 추천안으로 정하고 넘어간다.

결정 기록의 '정한 방식'은 다섯 가지로 나눈다. 사용자가 추천안을 그대로 따랐는지, 자기 판단을 넣었는지가 남아야 나중에 사용자나 개발 도구가 다시 검토할 지점을 찾을 수 있다.

| 정한 방식 | 뜻 |
|---|---|
| 추천안 선택 | (추천) 선택지를 골랐다 |
| 다른 선택지 | 추천이 아닌 선택지를 골랐다 |
| 직접 입력 | '기타'로 직접 적었다 |
| 자료로 확인 | 맥락 자료에서 읽은 것을 사용자가 맞다고 확인했다 |
| 추천안에 맡김 | 판단을 맡겨 추천안으로 정했다 |

### 길어질 때: 중간 점검

질문이 8개쯤 쌓일 때마다 중간 점검 질문을 하나 넣는다. 질문 본문에 지금까지 정한 개수와 남은 큰 가지를 한 줄로 적는다(예: '남은 큰 가지: 데이터, 화면 목록, 배포'). 선택지:

- `계속 (추천)`
- `남은 가지는 추천안으로`: 남은 가지를 추천안으로 채우고 '추천안에 맡김'으로 기록한 뒤 마무리로 간다
- `여기까지 정리`: 지금까지 정한 것과 남은 가지를 요약해 보여 준다. 다음에 이 요약을 붙여 넣으면 이어서 진행한다

## 4. 마무리

프론티어가 비면(트리의 모든 가지를 확인했고 조용히 가정한 것이 남지 않으면) 인터뷰를 끝낸다.

1. 확정된 결정을 짧은 목록으로 정리해 보여준다. 미정으로 남긴 항목과 받은 맥락 자료 목록을 따로 표시한다.
2. 이 정리가 맞는지 확인받는다. 고칠 점이 있으면 해당 가지로 돌아가 다시 묻는다. 앞에서 산출물을 이미 골랐으면 이 확인 질문에 산출물도 함께 적어 한 번에 확인받는다.
3. 산출물을 아직 고르지 않았으면 `AskUserQuestion`으로 묻는다.
   - 앱, 웹, 도구처럼 개발할 대상일 때
     - `개발 인계 세트 (추천)`: PRD와 개발 도구용 문서, 참고 자료, 시작 프롬프트까지
     - `PRD만`: PRD.md 한 장
     - `요약만으로 충분`: 여기서 종료
   - 그 밖의 주제(수업 계획, 의사결정 등)일 때
     - `PRD 만들기 (추천)`: 정리된 결정으로 PRD.md 작성
     - `요약만으로 충분`: 여기서 종료

사용자가 확인하기 전에는 결정 내용을 바탕으로 실행(코드 작성, 파일 생성 등)하지 않는다.

## PRD 작성 (PRD를 고른 경우)

`PRD.md`(또는 주제에 맞는 파일명, 예: `PRD-bubble-laundry.md`)를 파일로 만들어 사용자에게 전달한다. 인터뷰에서 사용자가 정한 내용만 쓰고, 정하지 않은 것을 지어내지 않는다. 미정 항목은 '열린 질문'에 남긴다. 해당 없는 섹션은 빼도 된다.

```markdown
# <제품/프로젝트명> PRD

## 1. 개요
- 한 줄 요약
- 배경과 문제

## 2. 목표와 비목표
- 목표
- 비목표(이번 범위에서 하지 않는 것)

## 3. 사용자
- 주 사용자와 특성(교육용이면 대상 학생의 수준과 특성)
- 사용 맥락(언제, 어디서, 어떤 기기로)

## 4. 핵심 기능
| 우선순위 | 기능 | 설명 |
|---|---|---|
| 필수 | | |
| 선택 | | |

## 5. 사용 흐름
1. ...

## 6. 기술·운영 조건
- 기술 스택, 배포, 데이터 저장, 보안·개인정보

## 7. 성공 기준
- 무엇을 보면 잘 됐다고 판단하는가

## 8. 일정

## 9. 열린 질문
- 인터뷰에서 미정으로 남은 항목

## 부록 1: 결정 기록
| 질문 | 선택 | 정한 방식 | 비고 |
|---|---|---|---|
| | | 추천안 선택 / 다른 선택지 / 직접 입력 / 자료로 확인 / 추천안에 맡김 | |

## 부록 2: 참고 자료
| 자료 | 보여 주는 것 | 따를 것 | 따르지 말 것 |
|---|---|---|---|
```

받은 맥락 자료가 없으면 부록 2를 뺀다. 전달 후에는 한 줄로 끝맺는다. 개발할 대상인데 PRD만 골랐다면 다음 단계로 개발 인계 세트 하나만 제안한다.

## 개발 인계 세트 (인계 세트를 고른 경우)

인터뷰 결과를 개발 도구가 실제로 읽는 자리에 나눠 담는다. 클로드 코드는 CLAUDE.md를, 코덱스는 AGENTS.md를 세션마다 자동으로 읽는다. 그래서 매번 지킬 규칙은 그 두 파일에, 자세한 내용은 문서에 둔다.

| 산출물 | 담는 것 |
|---|---|
| PRD.md | 무엇을, 왜, 누구를 위해 만드는지와 성공 기준 |
| AGENTS.md | 매번 지킬 규칙, 기술 스택, 문서 위치 |
| CLAUDE.md | `@AGENTS.md` 한 줄과 클로드 코드 전용 규칙 |
| DEVELOPMENT.md | 배포와 운영, 데이터, 개발 단계와 단계별 완료 확인 방법 |
| DESIGN.md | 화면 규칙, 분위기, 화면 목록, 참고 자료 설명 |
| references/ | 사용자가 준 이미지와 동영상 핵심 장면 캡처(학생을 알아볼 수 없는 것만) |
| 시작 프롬프트 | 개발 도구에 처음 붙여넣는 글. 파일로 만들지 않고 채팅에 코드박스로 제시 |

순서는 보충 인터뷰, 문서 작성, 전달이다.

### 1. 보충 인터뷰

인계 세트를 앞에서 골랐다면 아래 가지는 본 인터뷰에서 이미 물었으므로 남은 것만 확인한다. 마지막에 골랐다면 여기서 묻는다. 묻지 않고 문서를 채우면 정하지 않은 것을 지어내게 되기 때문이다. 진행 원칙과 질문 형식은 본 인터뷰와 같다.

점검할 가지:

- 새 프로젝트인지, 기존 프로젝트에 추가하는 것인지 (산출물 구성이 달라지므로 가장 먼저 확인)
- 기술 스택과 배포 위치
- 데이터: 무엇을 어디에 저장하는지, 로그인과 개인정보를 다루는지
- 학생 정보를 다루면 배포 전 보안·개인정보 점검을 개발 단계 마지막에 넣을지
- 개발 단계: 무엇부터 만들지, 단계마다 무엇을 보면 끝났다고 판단할지
- 사용 기기와 조작 방식(터치, 마우스 등)
- 화면 분위기: 색, 글꼴, 전체 인상 (맥락 자료로 정해졌으면 묻지 않는다)
- 사용자 특성에서 나오는 화면 규칙: 글자와 버튼 크기, 한 화면의 정보량, 문장 수준
- 주요 화면 목록
- 개발 도구가 지킬 작업 규칙과 하지 말아야 할 것

이미 정해진 가지와 이 프로젝트에 해당 없는 가지는 묻지 않는다.

기술 질문은 사용자가 개발자가 아닐 수 있다는 전제로 묻는다.

- 선택지 description에 그 선택이 사용자에게 무엇을 뜻하는지(비용, 난이도, 직접 해야 할 일)를 쉬운 말로 적는다. 기술 용어를 쓰면 무슨 뜻인지 한마디 붙인다.
- 사용자가 평소 쓰는 기술이 대화, 첨부 파일, 이전 대화, 메모리에서 확인되면 그것을 추천안으로 둔다. 확인되지 않으면 교사가 혼자 운영하기 쉬운 구성(예: React + Vite + Supabase + Vercel)을 추천안으로 둔다.
- 프로젝트 성격상 그 구성이 맞지 않으면(오프라인 우선, 데스크톱 전용 등) 억지로 끼우지 않고 맞는 대안을 추천안으로 둔다.

보충 인터뷰가 끝나면 추가로 정해진 것만 짧게 보여주고 확인받은 뒤 문서를 만든다.

### 2. 문서 작성

문서를 쓰기 전에 이 스킬 폴더의 `references/handoff-templates.md`를 읽고 그 템플릿을 따른다.

작성 규칙:

- **한 사실은 한 파일에만 적는다.** 같은 내용이 두 곳에 있으면 한쪽만 고쳐져 어긋난다. 다른 파일에서는 그 위치를 가리키기만 한다. 인계 세트의 PRD에서는 '기술·운영 조건'과 '일정' 섹션을 빼고 DEVELOPMENT.md를 가리킨다.
- **정한 것만 쓴다.** 미정 항목은 PRD의 '열린 질문'에 남긴다.
- **세팅해야 알 수 있는 것은 비워 둔다.** 실행 명령어와 실제 폴더 구조는 `(세팅 후 에이전트가 채움)`으로 남긴다. 없는 명령어를 적어 두면 개발 도구가 그대로 믿고 실행하다 막힌다.
- **AGENTS.md는 60줄 안팎으로 짧게 쓴다.** 세션마다 통째로 읽히는 파일이라 길수록 매번 부담이 된다. 설명이 길어지면 문서로 옮기고 가리킨다.
- **CLAUDE.md와 AGENTS.md를 두 벌로 쓰지 않는다.** 본문은 AGENTS.md에 쓰고, CLAUDE.md에는 그 파일을 불러오는 `@AGENTS.md` 한 줄을 둔다. 클로드 코드에만 해당하는 규칙이 있을 때만 그 아래에 덧붙인다.
- **참고 자료를 개발 도구에 넘긴다.** 받은 이미지는 영문 파일 이름(예: `ref-01-main-sketch.png`)으로 references 폴더에 넣고, DESIGN.md의 '참고 자료' 표에 각 자료에서 무엇을 따르고 무엇을 따르지 말지 적는다. 동영상은 넣지 않고 핵심 장면 캡처만 넣는다. 학생을 알아볼 수 있는 자료는 넣지 않는다.
- 화면이 없는 프로젝트면 DESIGN.md를 만들지 않는다. 받은 자료가 없으면 references 폴더와 '참고 자료' 섹션을 뺀다. 해당 없는 섹션은 뺀다.

구성은 새 프로젝트인지 기존 프로젝트인지에 따라 다르다. `<slug>`는 프로젝트나 기능 이름을 영문 소문자와 하이픈으로 옮긴 것이다. 압축을 풀 때 한글 이름이 깨질 수 있으므로 폴더와 파일 이름에는 한글을 쓰지 않는다.

**새 프로젝트**: 폴더 하나에 담고, 이 폴더가 그대로 프로젝트 폴더가 된다.

```
<slug>/
  AGENTS.md
  CLAUDE.md
  docs/
    PRD.md
    DEVELOPMENT.md
    DESIGN.md
    references/
```

**기존 프로젝트에 추가**: 기존 지침 파일을 덮어쓰면 그동안 쌓인 규칙이 사라진다. 그래서 AGENTS.md와 CLAUDE.md는 만들지 않고, 기존 파일에 합칠 조각(`AGENTS-add.md`)만 만든다. 폴더 하나에 담아 프로젝트 폴더 안에 넣게 한다. DESIGN.md에는 기존 화면 규칙과 달라지는 것만 적고, 달라지는 것이 없으면 만들지 않는다.

```
handoff-<slug>/
  PRD.md
  DEVELOPMENT.md
  DESIGN.md
  AGENTS-add.md
  references/
```

### 3. 전달

1. 파일을 만들고, 폴더째 zip 하나로 묶어 사용자에게 전달한다. zip을 만들 수 없는 환경이면 파일을 하나씩 전달한다.
2. 마지막 답변은 아래로만 쓴다.
   - 한두 줄: 무엇을 전달했는지와 폴더를 어디에 두는지. 새 프로젝트면 압축을 푼 폴더를 프로젝트 폴더로 쓰고, 기존 프로젝트면 그 폴더를 프로젝트 폴더 안에 넣는다.
   - 참고 자료를 zip에 넣지 못한 환경이면 한 줄: 어떤 자료를 어떤 파일 이름으로 references 폴더에 넣을지.
   - 시작 프롬프트: 코드박스 하나에 일반 텍스트로 제시한다. 제목 기호나 굵게 같은 마크다운 서식을 쓰지 않고, 파일로 만들지도 않으며, zip에도 넣지 않는다. 사용자가 복사해서 개발 도구에 바로 붙여넣는 글이기 때문이다.
3. 그 밖의 설명이나 다음 단계 제안은 붙이지 않는다.
